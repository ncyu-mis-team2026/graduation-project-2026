## 二、討論紀錄

### （一）方法論流程圖檢討：需求分析須在功能設計之前

- 目前流程圖的順序是「每週會議討論 → 提出九大功能模組對應痛點 → 收集使用者意見」，順序不合理。
- 系統分析應**先做需求分析**：功能模組代表系統要設計成哪些模組，需求一定要在功能模組設計之前產生。
- 建議將「初步功能設計」移到**問卷設計、發放、回收與分析之後**；需求分析完成後，才進入系統設計。
- 目前流程圖把「系統分析與設計的階段」和「專題團隊的運作方式」（如每週會議）混在一起，應分開呈現。
- 流程是動態的，不是完全的瀑布式，各階段可回頭修正。

### （二）教授建議的方法論架構

- **需求分析階段**（前幾個月實際在做的事）：
  - 腦力激盪、確認主題
  - 競品調查（寵物協尋及遊戲化相關產品）
  - 使用者訪談
  - 問卷調查與分析
  - 若要寫多一點，可加入文獻探討
- **系統設計階段**（採用敏捷開發流程）：
  - 需求定義：User Story／Use Case
  - 資料需求分析：ER Model
  - 流程需求分析：DFD
  - 每次 Sprint 都要產出看得到的 MVP 雛形
  - 每項工作都要對應到 DoR／DoD 所定義的內容；每次 Sprint 修改完一組再做下一組，不斷循環
- **2027/1/6 的兩項產出**：
  1. 專題文件（專題提案書）
  2. 關鍵模組的雛形
- 專題文件中被規定要做的各項內容，都可以對應到流程圖中的各個環節，在每次循環中逐步完成。
- 教授當場畫了修正版流程圖，會把檔案（第四頁）上傳給組員，組員可再修改成自己的版本。
- 差異化的重點：現在大家都用 AI 做專題，題目本身差異不大；要放入**真實、別人沒在做的元素**（如實際的使用者訪談），並把開發專題的方法論融合進去，讓評審看到需求是如何產生、規格如何一步步訂出、功能如何排序與驗證。
- 目前**使用者訪談尚未進行**，只定出問卷（上次已 Review 過）。

### （三）期中報告短劇規劃（學生報告）

- 以學長訪談內容改編成短劇劇本，約 10 分鐘、分成五幕，依學長的經歷發展：
  - 大學時期迷惘、成績不理想
  - 考研究所
  - 實習與 Side Project
  - 選擇研發替代役而非直接就業（錄音較不清楚，請確認）
  - 現在用 AI 寫程式的狀況，並給學弟妹建議
- AI 那一幕可做對比：舞台分兩邊，一邊是以前花很久 Debug，另一邊是現在直接叫 AI 寫程式。
- 報告時間：組員原先認為每組 12 分鐘，經確認**正式報告每組 10 分鐘**，劇本長度需配合調整。
- 呈現方式：以 **PPT 輔助演戲**，重要資訊放在 PPT 上。
- 時程：
  - 10/30 期中考週，會議暫停一次
  - **11/6 會議時彩排一次**
  - **11/11 正式報告**

### （四）教授對短劇的建議

1. **掌控時間**：確定時間能夠控制在規定內。
2. **劇本與 PPT 要兜起來**：目前 PPT 尚未完成，11/6 彩排時需一併確認。
3. **每一幕要有明確的主要訊息**：
   - 演戲有舞台效果、比較有趣，但若只是大家笑一笑，最後可能沒有留下任何東西；PPT 則能讓資訊較豐富、明確。
   - 不只演出「他做了什麼」，更要呈現 **How（如何做）、Why（為什麼這樣做）以及產生了什麼效果、學到什麼**。例如：實習中看到哪些在學校看不到的東西、如何挑選實習公司、如何決定做什麼 Side Project、Side Project 發揮了什麼效果。
   - 可參考上次張雅茹那組的呈現：轉換階段遭遇的困境、如何克服、學到什麼。
   - 每幕要傳達的訊息不一定要用演的，可在換幕時打在 PPT 上。

### （五）GitHub 看板展示與 User Story 運用

- 組員展示 GitHub Projects 看板初步設計，分為**待辦、開發中、審查中、已完成**四個階段，卡片可拖曳移動，掌握每個切分出來的任務目前狀態；目前對整體操作還不熟悉。
- 教授說明：
  - 真正的重點（「肉」）是**從需求把所有 User Story 列出來**（使用教授提供的模板），並以 **MoSCoW 原則**排定優先順序。
  - 看板只是流程控管機制，可在 GitHub 上做，也可用其他看板系統；GitHub 的好處是 Issue 可對應到程式碼，整合性較高。若打算用 GitHub 做看板與版本控管，可透過 AI 研究做法。
  - 目前只有抽象的九大模組圖（分使用者端與後台），需釐清各模組對應哪些 User Story（例如列出約 30 個）。
  - User Story 之後會轉換成 Use Case，繪製 DFD、ER Model 時也要回頭參考 User Story。
  - Sprint 範例：使用者訪談完成後，先做「協尋子系統」，挑出其中幾個 Story，連同資料需求、DFD、Use Case 在該次 Sprint 中弄清楚，甚至做出簡單的畫面雛形。
- **AI 的運用方式**：
  - User Story 不能叫 AI 產生，因為那是真正的使用者需求。
  - User Story 列好後，可請 AI 先產生 DFD、ER Model、Use Case 圖的初稿，再由組員修正；如此每次 Sprint 都更新一版才可行，若全部手工做則較困難。
  - 可在實作過程中詢問 AI 如何將敏捷開發方法與 AI 輔助產出結合。
- 評審常問「有沒有做實際的使用者訪談、調查」，必須有真正非 AI 產生的資料，才能回答問題。
