**1.AI坐姿守護精靈**  
一、研究動機與目標客群

* **研究動機:**  
  現代人工作繁忙，經常在辦公、書桌前一坐就是好幾個小時，如果坐姿又不正確的話，就有可能對腰椎、背部造成影響。  
* **目標客群:**  
  需長時間辦公或使用電腦的久坐族群，如「大學生」與「辦公室上班族」。  
* **核心痛點:**  
1. 無意識的姿勢不良:專注工作時容易不自覺駝背，但是自己很難察覺。  
2. 久坐忘記休息:一坐就是好幾個小時，容易導致肩頸僵硬，甚至引發及追問題。  
3. 不知坐姿是否正確:不知道自己的坐姿是否正確，以及具體哪裡錯誤。

二、系統構思與商業模式

* **產品構思:**透過側邊架設的手機鏡頭進行全身側面骨架捕捉的系統。  
1. 全身異常偵測：捕捉脊椎弧度、翹腳或肩膀高低不平，只要超出標準角度即發出提醒。  
2. 針對性舒展處方： 系統會根據你今天哪個部位姿勢錯最久，自動推薦專屬該部位的舒展動作。  
* **商業模式:**  
1. B2C:採訂閱制，基礎偵測功能免費。若需要進階數據、進階功能則須付訂閱費。  
2. B2B:與椅子廠商合作，當作軟硬體整合商品。

三、產品可行性

* **市場規模:**現代人花錢照顧自己的脊椎健康越來越平常，如:購買人體工學椅、找物理治療師。  
* **競爭產品分析:**SitApp、Postura等電腦視訊鏡頭偵測軟體  
* 優點:硬體成本低、無感監測  
* 缺點:偵測盲區大(只有拍到正面上半身)

* **產品優勢:**能夠更精準的偵測全身姿勢異常，而不是只有掃描上半身，從根本解決使用者下背或骨盆問題。

四、技術可行性

* **AI辨識:**使用姿勢偵測開源模型，如YOLO，來抓取全身關節點計算角度  
* **領域知識與邏輯轉換:**將物理治療或人體工學的基礎標準等知識，轉化為計算角度的邏輯。

五、預期困難

* **專業知識來源:**我們並非物理治療專業背景，難以準確界定醫學上「錯誤姿勢」的標準。  
* **環境視線遮蔽：**每個使用者的桌面佈置與椅子款式差異大。鏡頭掃描視線可能被阻擋。

**2.喵了個咪**  
一、研究動機與目標客群

* 研究動機:  
  本專案希望透過類似於「寶可夢」的抓寶機制吸引大眾並建立街貓目擊記錄，並藉此建立地區貓咪資料庫，同時在地圖上標記貓咖及網路上較有名氣的明星貓所在的店家。這不僅是一項愛貓人士休閒娛樂，更能幫助解決寵物貓走失的問題。  
* 目標客群:  
1. **核心客群**：貓咪飼主與廣大貓咪愛好者。  
2. **商業客群**：實體貓咖與寵物友善店家。  
* 核心痛點:  
1. **走失協尋效率問題**：愛貓走失時，傳統協尋方式（如紙本或社群媒體上的零散貼文）效率較低下，且缺乏精準區域定位對比。  
2. **貓的攝影平台彙整**：許多人受限於環境無法飼養貓，但仍喜愛與貓的互動。同時，貓咪攝影愛好者通常將照片發布於自身社群平台，目前缺乏一個能將零散照片彙整的平台。

二、系統構思與商業模式

* 產品構思:  
1. **走失協尋網**：將玩家抓捕街貓產生的 GPS 座標標記為「街頭目擊」，搭配飼主發布懸賞令，系統會自動撈取區域內名單進行比對。同時，懸賞令可一鍵同時發布至 Threads 等平台，提高曝光度，提高寵物尋回效率、機率。  
2. **貓咪收藏錄**：玩家路上遇見貓時，可藉由道具進行「捕捉」，系統透過 2D 命中判定與 AI 辨識生成專屬的貓咪虛擬卡牌收錄進圖鑑。  
3. **貓咪地圖**：地圖提供目擊記錄、寵物友善商家與貓咪咖啡廳等，並與有意願商家達成合作。  
4. **其餘玩法**：  
   1. 走路種貓草：透過走路里程數換取抓捕貓所需的道具。  
   2. 貓咪團體戰：玩家藉由BOSS對戰方式抓捕地區限定徽章的貓。  
   3. 玩家對戰：玩家可自由組隊進行對戰，並且獲取牌階。  
* 商業模式:  
1. **B2C消費者儲值服務**（免費版/訂閱版）：  
   1. 體力與道具資源  
   2. 觀看廣告換取資源  
   3. 特色卡牌外觀  
   4. 黃金懸賞令次數。  
2. **O2O實體店家合作**：以實體店內限定解鎖方式，玩家須進入店內消費並進行掃描 QRcode 以獲得限定卡牌。  
3. **爭取政府補助**：透過玩家辨認貓是否有剪耳判別是否絕育，將未絕育街貓地圖結合動保處TNR，提高流浪動物絕育律。

三、產品可行性

* 競品分析與差異化優勢：  
  * 純遊戲競品（如 CatchCat 等）：市面上的類似產品主要以單純「娛樂與收集慾」，缺乏走失協尋等實用功能。相較而言，本專案不僅提供了娛樂面向，更具備了協尋走失寵物的價值。  
  * 一般社群平台：傳統社群的協尋依賴演算法的隨機擴散，資訊亦沉默且精準度較低。本專案透過「街頭目擊」功能，能更快的匹配特徵相似的寵物並提供曾出沒地點，大大提升了走失尋回的機率。  
* 市場可行性：  
  * 台灣寵物市場龐大，且考慮到飼主對於寵物走失的焦慮感極高，因此推測飼主對於能增加尋回機率的工具的需求及使用意願不低。同時，結合O2O實體導流模式，能有效地向在地店家提案合作。

四、技術可行性

* **前端**：改採 Android 原生(Java/Kotlin)或 Flutter 開發。利用基礎 2D 動畫與「座標直線距離公式」完成抓捕判定。  
* **AI辨識與生成**：串接 Google ML Kit進行實景貓咪辨識，後續搭配影像處理API完成去背與卡牌風格化。   
* **後端與資料庫**：Redis 搭配 MySQL。

五、預期困難

1. 資料來源：沒有貓。  
2. 走失協尋的對比邏輯：AI很難辨識兩者是否為同一隻貓，或許要用篩選法。  
3. AI辨識限制：玩家如果對著照片也可以捕捉成功，代表辨識不夠嚴謹。

**4.吉他家教**

* 研究動機: 本專案希望打造一套「AI 吉他學習教練」系統，讓學習者能以任何一首自己想彈的歌曲作為學習起點，透過 AI 自動辨識歌曲的和弦、曲調與難度，並依照個人程度、正在練習的歌曲與過往練習紀錄，提供客製化的練習計畫與即時問答指導。  
    
* 目標客群:  
1. 核心客群：自學吉他的初階學習者，尤其是希望透過彈唱特定流行歌曲進行學習的族群。  
2. 潛在客群：吉他教師、音樂教室與線上音樂教育平台，可作為輔助教學或補充教材工具。  
* 核心痛點:  
1. 教學內容缺乏個人化：市面上教材與 YouTube 教學影片多為跟著彈，無法依據學習者的程度、想學的歌曲給予對應建議，遇到問題時也無法即時解答  
2. 缺乏長期進度追蹤與回饋機制：多數自學者沒有系統化記錄練習內容的習慣，既無法回顧自己的成長軌跡。  
3. 真人教學資源取得成本高：一對一吉他課程費用較高且受限於時間地點，難以做到隨時隨地、依需求即時提問與調整練習內容。

### **二、系統構思與商業模式**

* 產品構思:  
1. 歌曲拆解引擎:使用者輸入歌名或上傳音檔,系統自動進行和弦辨識、曲調分析與難度評分,並標註出歌曲中最困難的段落,同時給出建議的分段練習順  
2. AI 教練:學習者可隨時以中文提問任何吉他相關問題,AI 會結合使用者當前程度、正在練習的歌曲與過往練習紀錄,給出針對性的回答與示範建議  
3. 個人化練習計畫:根據學習者選定的目標歌曲與自評(或系統評估)程度,自動產生每日練習菜單,明確標示今日練習項目、建議時長與重點技巧,並隨練習成果動態調整後續計畫。  
4. 練習進度追蹤:記錄每次練習的內容、時長與自評完成度,以視覺化方式呈現學習曲線,讓 AI 教練能依據長期數據,隨時間給出越來越貼近個人狀況的建議。  
* 商業模式:  
  B2B2C 教學端合作:與音樂教室、吉他老師合作,提供教學輔助版本,協助老師管理學生練習進度並自動生成教材,依帳號數或教室規模收取授權費用。

### **三、產品可行性**

* 競品分析與差異化優勢:  
1. 純教學平台競品(如 Yousician、Simply Guitar 等):多以固定教材、遊戲化關卡引導學習,曲庫選擇有限且都只有英文且缺乏「任意歌曲」的即時分析能力,也無法針對個人問題進行自然語言互動。相較而言,本專案讓使用者能以「任何一首想學的歌」作為學習起點,並提供個人化的 AI 對話式指導。  
* 市場可行性:  
   自學樂器的族群龐大,,但坊間資源多為單向教學,缺乏互動與個人化引導。本專案切中「想學的歌沒教材」與「希望有人教學」,推測學習者對於能即時解惑、規劃練習的工具有較高付費意願。

### **四、技術可行性**

* 前端:採 Flutter 跨平台開發,搭配音檔上傳與播放介面,並整合和弦圖、指法圖等視覺化教學元件。  
* AI 辨識與分析:串接音訊處理與和弦辨識模型(如結合開源和弦辨識演算法或音樂資訊檢索 API)進行曲調與和弦辨識,搭配大型語言模型(如 Claude API)處理 AI 教練對話、練習計畫生成與難度標註等自然語言任務。  
* 後端與資料庫:採用 PostgreSQL 儲存使用者練習紀錄與歌曲分析結果,搭配 Redis 處理即時對話快取與 session 管理。

### **五、預期困難**

1. 和弦辨識準確度:市售歌曲版本多樣(現場版、翻唱版、變調版),音訊辨識容易受伴奏樂器、人聲干擾,影響和弦判斷準確性。  
2. 難度評分標準不易量化:「難度」涉及封閉和弦、節奏型態、轉換速度等多重因素,如何建立客觀且符合初學者實際感受的評分機制,需要大量測試與調整。  
3. 個人化建議的資料冷啟動問題:新使用者缺乏練習紀錄,AI 教練初期難以給出真正貼合個人狀況的建議,需設計初始評估機制彌補資料不足。  
4. 音樂版權議題:歌曲音檔辨識與曲庫使用可能牽涉版權授權問題,需評估合法取得或分析歌曲資料的方式。

1. ### 演出資訊聚合引擎:整合全台主要 livehouse 與售票平台(The Wall、Legacy、indievox 等)的演出資訊,建立統一資料庫,使用者不需再逐一造訪各個網站查詢。

2. ### Spotify 串接與喜好分析:使用者以 Spotify 帳號登入並授權,系統分析其聆聽紀錄,建立個人音樂喜好檔案。

3. ### AI 個人化推薦:比對使用者喜好檔案與演出資料庫,推薦風格相近的台灣獨立樂團演出,並依據使用者的收藏與出席紀錄持續優化推薦準確度。

4. ### 樂團探索頁面:以「因為你喜歡 OO,你可能會喜歡這個獨立樂團」的形式推薦新樂團,並附上試聽連結與近期演出場次,降低樂迷認識新團的門檻。

5. ### 訂閱與通知機制:使用者可收藏喜歡的樂團,當該樂團公布新演出時自動推播通知。

6. ### 篩選與地圖功能:提供依風格、地點、票價、日期篩選演出的介面,並在地圖上顯示鄰近演出場次。

* ### 商業模式:

1. ### B2C 加值服務:基礎瀏覽與推薦免費使用,進階功能(如多樂團行程規劃)採訂閱制。

### **三、產品可行性**

* ### 競品分析與差異化優勢:

  * ### 售票平台(KKTIX、iNDIEVOX):功能聚焦於賣票,資訊呈現以場館/主辦方自行上架為主,缺乏跨平台整合與個人化推薦機制

* ### 市場可行性:    台灣現場音樂展演場館數量持續成長,獨立樂團與樂迷社群黏著度高,對探索新團與不錯過喜愛樂團演出皆有實際需求。同時串流音樂已是多數樂迷的日常聆聽習慣,以 Spotify 聆聽資料作為推薦基礎,能降低樂迷建立喜好檔案的操作門檻,提升採用意願。

### **四、技術可行性**

* ### 前端:採 Flutter 或 React Native 跨平台開發,搭配地圖 SDK(如 Google Maps)呈現演出地點分佈與篩選介面。

* ### Spotify 串接:透過 Spotify 官方 Web API 的使用者授權登入(OAuth),讀取使用者已同意分享的個人聆聽資料(如常聽歌手、播放清單),作為推薦系統的輸入特徵。

* ### 推薦系統:以協同過濾或內容基礎推薦(content-based filtering)模型,比對使用者音樂特徵與樂團風格標籤,產生個人化演出推薦。

* ### 演出資料整合:針對有公開 API 或開放資料的售票平台優先串接;沒有開放介面的場館

* ### 後端與資料庫:PostgreSQL 儲存演出資料與使用者收藏紀錄,搭配排程系統(如 Cron Job)定期更新演出資訊與推播通知。

### **五、預期困難**

1. ### **Spotify API 使用限制**:Spotify近期大幅緊縮開發者可透過 API 存取的功能,本專案在做「聆聽喜好分析」時,能取得的資料類型可能比預期更有限(例如僅能取得使用者常聽的歌手/曲目列表,而非深入的音訊特徵),推薦模型的精準度與可行的分析維度需要重新評估,並需持續關注 Spotify API 條款變動。

2. ### **演出資訊爬取的合法性與穩定性**:需個別檢視各平台的服務條款是否允許爬蟲存取,長期依賴爬蟲也有資料來源不穩定、格式異動需持續維護的風險。

3. ### **商業合作洽談門檻**:許多獨立 livehouse 與樂團規模小、資源有限,是否願意配合平台上架資料
