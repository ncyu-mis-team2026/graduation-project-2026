## 一、會議目的

1. 教授建議本專題導入敏捷開發 Scrum 進行專案管理，並說明其流程、角色分工與相關模板。

## 二、討論紀錄

### （一）為何導入 Scrum：避免瀑布式開發的問題

- 7 至 9 月主要在建立專題題目與功能的共識；方向較明確後，開始大量撰寫分析文件（需求、功能模組、DFD、ER Model、技術選型等），逐漸變成「瀑布式開發」。
- 瀑布式的問題：上學期寫好的規格，到下學期實際開發時常與原本講的不一樣，問題要到很晚才浮現。
- 建議做法：將現有功能切細、排定優先順序、指派負責人，以 **Sprint（衝刺）** 方式邊做邊寫文件。每次衝刺都產出可展示的小系統（MVP），問題在實作中提早浮現，同步修正文件、程式與畫面。
- 業界軟體公司與資訊部門多以 Scrum 管理專案，先在專題中練習有助於未來就業。

### （二）Sprint 規劃建議

- 每次 Sprint 約 **2 週**，從現在到明年 6 月約可安排 12～15 次。
- 範例排程：
  - Sprint 0：整體規劃（角色分工、工作協議、產品待辦清單）
  - Sprint 1～2：完成「協尋」相關功能
  - Sprint 3～5：完成「遊戲化」相關功能
  - 之後：驗證、測試等也要排入
- 系統功能分為兩大類：**協尋** 與 **遊戲化**，各自用使用者故事（User Story）串起來說明。
- 有固定的截止日（2027/1/6 期中簡報、明年 5～6 月成果繳交），因此**不需製作燃盡圖，也不需做速度追蹤**。

### （三）角色與分工

- **Product Owner（產品負責人）**：至少選出一人掌握全貌，決定產品待辦清單的優先順序及哪些功能要做、哪些不做。
- **輪值主席**：如同現行每週輪流主持會議，負責主持會議並維護看板。
- **Developer（開發者）**：每人負責一個功能領域，從實作、測試到文件一手包辦。例如：
  - 成員 A：尋寵雷達相關功能
  - 成員 B：建立寵物角色（貓、狗）、進化、偵測等相關功能
  - 成員 C：協尋案件的完整流程（發布協尋、通報處理、結案）
- 跨任務需協調的事項（如資料庫設計、流程串接、畫面風格統一）在會議中討論。
- 次要職責：文件、海報、影片等，每次 Sprint 重新分配。

### （四）會議形式

- **Sprint 規劃會議**：每次 Sprint 開始時訂定故事線，拆解成任務，明確產出目標與驗收條件。
- **每日站會（選擇性）**：每天 10～15 分鐘，每人報告三件事：昨天完成什麼、今天要做什麼、需要誰協助。無法每天開會者可改用通訊軟體在固定時間發文回報。
- **每週會議（必要）**：Review（審查）時實際展示這 1～2 週做出的畫面與功能（例如登入畫面、不同身分看到的畫面、協尋公告的張貼與通報處理流程）。
- **Retrospective（回顧會議）**：每次 Sprint 結束後檢討規劃與執行的問題（估算過於樂觀或悲觀、規劃太模糊等），在下一輪改進。
- 每日站會非強制，由組員自行決定；每週會議必須持續進行。

### （五）User Story 與驗收條件寫法

- 格式：「身為 **〔角色〕**（玩家、需要協尋的飼主、路人、管理者），我想要 **〔功能〕**，以便 **〔價值／目的〕**。」
- Story 要盡量切細，例如將「拍攝寵物照片」與「收集卡牌」拆成不同的 Story。
- 單一 Story 不應需要兩個月才能完成；太大就繼續切，讓 2 週內能看到成果。
- 驗收條件須明確可驗證，每個 Story 寫 2～4 條，例如：
  - 拍照後 10 秒內產生卡牌
  - 拍攝照片時自動去背
  - 卡牌可存入個人圖鑑

### （六）教授提供的模板內容

- **團隊章程**：成員職責（含 Product Owner）、輪值表、工作協議（是否開站會或週會、訊息回覆時限、PR 合併前至少一人 Code Review、使用工具、請假、決策衝突處理）。
- **產品願景板**：一句話說明為什麼要做這個專題（範例目前只針對尋寵，需再補上遊戲化）。
- **Sprint 規劃表**：每次 Sprint 的時間、里程碑與目標。
- **產品待辦清單（Product Backlog）**：所有功能規格化為 Story，標註角色、驗收條件、MoSCoW 優先度（Must / Should / Could / Won't）、故事點、對應 Sprint、狀態與負責人。
- **Sprint 待辦清單（Sprint Backlog）**：從產品待辦清單中挑出該次 Sprint 的任務，解析度較細。
- **DoR / DoD**：定義「準備就緒」與「完成」。完成須通過程式、測試、功能與文件檢查。
- **看板**：區分待辦、開發中、審查中、已完成，讓全組隨時掌握進度。工具可用 Excel、Jira 或 GitHub Projects（後者可與 Issue、PR 連動）。

### （七）Scrum 的好處與成本

- 好處：專題進行較有計畫、有規律；每人的貢獻（PR、Code Review、Commit 數、會議互動）都有清楚紀錄；可避免歷屆常見問題，例如做完無法 Demo、一人寫程式一人寫報告、故事太大沒有結論、變成老師在追學生進度。
- PR 審查建議訂定回覆時限（例如最晚 3 天內回覆），彼此督促。
- 缺點：需要花時間，但重點在養成習慣，不需要花很多時間。
- 教授強調此為建議，**不強制**，由組員自行決定是否採用。

### （八）功能範圍檢討（學生討論）

- 目前已列出 20 多個功能，先全部列入待辦清單，之後再透過迭代逐步修正，刪除非必要的功能。

- 以短週期反覆修正，避免像過去一樣規格定死，到開發時才發現問題。

### （九）技術測試回報：地圖定位 API

- 目前測試一套開源地圖服務（錄音聽寫為「Open Streamer」，應為 OpenStreetMap 相關服務），可透過 API 進行定位與地點查詢。
- 遇到的問題：

  - 大量標記時可能有問題。
- 有聽說部分 API 需要收費；目前使用的免費額度本月可能已超過，需再確認後續費用與替代方案。

## 三、決議事項

1. 是否全面導入 Scrum 由組員自行討論決定；教授已提供相關模板。
2. 若導入 Scrum：不製作燃盡圖、不做速度追蹤；每日站會自行決定是否實施；每週會議持續進行。
3. 功能清單先全部列入產品待辦清單，再以 MoSCoW 排序並於迭代中刪減；尋寵、協尋功能列為 Must。
